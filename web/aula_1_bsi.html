Semana 1: Arquitetura de Redes para Web & Injeção HTTP Bare-Metal

Nesta primeira semana, desconstruímos a abstração do navegador. A Web não é uma coleção de arquivos abertos localmente, mas um ecossistema de requisições de rede enviadas por canais TCP em formato de bytes brutos padronizados pela RFC 7230.

1. Socket & Rede

Rastrear o encapsulamento desde o Handshake TCP até a abertura do socket no SO.

2. Sintaxe CRLF

Compreender a necessidade física dos bytes 0x0D 0x0A na RFC 7230.

3. Injeção Manual

Injetar payloads brutos via netcat e diagnosticar respostas via curl -v.

Módulo 1

1. Da Física ao Socket TCP

A comunicação web na camada de aplicação depende da infraestrutura subjacente de transporte. Antes que qualquer caractere do protocolo HTTP possa ser interpretado pelo servidor, o sistema operacional do cliente precisa resolver o endereço do destino e fechar um contrato de conexão bidirecional confiável.

Sequência de Estabelecimento de Conexão Web

sequenceDiagram autonumber participant C as Cliente (Browser / Netcat) participant D as Servidor DNS participant S as Servidor HTTP (Porta 80) Note over C,D: Resolução de Nome de Domínio C->>D: Consulta A Record (example.com) D-->>C: Retorna IP (93.184.215.14) Note over C,S: Handshake TCP (Três Vias) C->>S: TCP SYN (Porta Destino: 80) S-->>C: TCP SYN-ACK C->>S: TCP ACK (Socket Aberto no SO) Note over C,S: Camada de Aplicação (HTTP/1.1) C->>S: GET / HTTP/1.1\r\nHost: example.com\r\n\r\n S-->>C: HTTP/1.1 200 OK (Payload + Headers) Note over C,S: Encerramento do Socket S->>C: TCP FIN (Connection: close) C-->>S: TCP ACK

Abstração do Socket no SO

No nível do sistema operacional, o socket é tratado como um descritor de arquivo (*File Descriptor*). Operações de rede realizam escrita e leitura em buffers de memória:

int sockfd = socket(AF_INET, SOCK_STREAM, 0);
connect(sockfd, &serv_addr, sizeof(serv_addr));
write(sockfd, "GET / HTTP/1.1\r\n...", len);
read(sockfd, buffer, sizeof_buffer);

Métricas da Camada de Transporte

  • DNS Lookup: Tempo para converter hostname em endereço IP.
  • Initial Connection: Latência do RTT (*Round Trip Time*) para concluir o SYN $\rightarrow$ SYN-ACK $\rightarrow$ ACK.
  • TTFB (Time to First Byte): Intervalo entre o envio do último byte do cabeçalho de requisição e a chegada do primeiro byte da resposta do servidor.
Módulo 2

2. A RFC 7230 & Anatomia da Mensagem HTTP/1.1

O protocolo HTTP/1.1 é estritamente baseado em texto ASCII. Por ser uma transmissão sobre stream de dados TCP (onde não há delimitação nativa de mensagens), o parser do servidor necessita de marcadores exatos de término de linha.

O Delimitador Obrigatório: CRLF (\r\n)

Na RFC 7230, cada linha do cabeçalho MANDATORIAMENTE deve ser finalizada pela sequência de dois bytes:

Carriage Return (\r): ASCII 13 / Hex 0x0D
Line Feed (\n): ASCII 10 / Hex 0x0A
Fim dos Headers: \r\n\r\n (CRLF duplo)

Estrutura da Requisição HTTP

CLIENT → SERVER
GET /index.html HTTP/1.1 \r\n
↑ Start Line: <Método> <URI> <Versão>
Host: example.com \r\n
User-Agent: BareMetalClient/1.0 \r\n
Accept: text/html \r\n
↑ Headers (Pares Chave: Valor)
[Linha em Branco Obrigatória] \r\n
↑ CRLF Duplo sinaliza o fim do cabeçalho
[Corpo/Payload Opcional]

Estrutura da Resposta HTTP

SERVER → CLIENT
HTTP/1.1 200 OK \r\n
↑ Status Line: <Versão> <Código> <Frase>
Content-Type: text/html \r\n
Content-Length: 48 \r\n
Connection: close \r\n
↑ Headers de Resposta
[Linha em Branco Obrigatória] \r\n
<html><body><h1>OK</h1></body></html>
↑ Body / Payload HTML
Módulo 3

3. Anatomia da URI / URL & Codificação Percent-Encoding (RFC 3986)

Toda requisição HTTP começa com a localização do recurso. A **RFC 3986** formaliza a sintaxe genérica do **URI** (Uniform Resource Identifier), do qual a **URL** (Uniform Resource Locator) é o subconjunto mais utilizado no contexto Web.

URI (Identificador Genérico)

Superconjunto que identifica um recurso por nome, localização ou ambos.

URL (Localizador de Recurso)

Especifica como acessar o recurso fornecendo seu protocolo de rede e localização (ex: https://...).

URN (Nome do Recurso)

Identifica o recurso de forma persistente por nome, independente da localização (ex: urn:isbn:0451450523).

Desconstrução de uma URL HTTP Completa

https://api.exemplo.com:443/v1/usuarios/42?status=ativo&limit=10#secao-detalhes
Scheme (Esquema)

Define o protocolo a ser utilizado pela camada de aplicação (http, https, ftp).

Host / Authority

Endereço IP público ou nome DNS resolvido para conectar o socket TCP.

Port (Porta TCP)

Porta de destino no servidor. Padrão: 80 para HTTP e 443 para HTTPS.

Path (Caminho)

Hierarquia do recurso no servidor. É a URI enviada na linha inicial do HTTP (GET /path...).

Query String (Consulta)

Pares chave-valor (?k1=v1&k2=v2) para filtrar/parametrizar a requisição sem alterar a rota base.

Fragment (Âncora)

Processado apenas pelo cliente (Navegador)! NUNCA é transmitido na linha de requisição ao servidor TCP.

Percent-Encoding (URL Encoding)

URIs só podem conter um conjunto restrito de caracteres ASCII imprimíveis (caracteres não reservados e reservados). Caracteres especiais, espaços ou caracteres Unicode (como acentos e emojis) devem ser convertidos para a notação %HEXHEX do byte equivalente em UTF-8:

Espaço ( ): %20 ou +
Caractere "ç": %C3%A7
Caractere "&": %26
Módulo 4

4. Métodos HTTP: Semântica, Idempotência e Segurança

Na especificação HTTP, os métodos (verbos) indicam a ação pretendida sobre o recurso identificado pela URI. Em Engenharia de Software e Redes, é vital diferenciar métodos por suas propriedades formais: **Segurança (Safe)** e **Idempotência (Idempotent)**.

Métodos Seguros (Safe)

Não alteram o estado do servidor (operações de consulta/leitura pura). Podem ser chamados sem causar efeitos colaterais na base de dados.

Idempotência

Executar a requisição $N$ vezes produz exatamente o mesmo resultado no estado do sistema que executá-la apenas 1 vez (essencial para mecanismos de retransmissão automática em falhas de rede).

GET
SAFE IDEMPOTENT

Solicita a representação de um recurso. Não deve conter payload no corpo da requisição.

GET /api/v1/users HTTP/1.1
POST
NON-SAFE NON-IDEMPOTENT

Submete uma entidade ao recurso especificado, frequentemente causando mudança de estado ou criação no servidor.

POST /api/v1/users HTTP/1.1
PUT
NON-SAFE IDEMPOTENT

Substitui completamente todas as representações atuais do recurso de destino pelos dados enviados.

PUT /api/v1/users/42 HTTP/1.1
PATCH
NON-SAFE NON-IDEMPOTENT

Aplica modificações parciais a um recurso (diferente do PUT que exige a substituição total).

PATCH /api/v1/users/42 HTTP/1.1
DELETE
NON-SAFE IDEMPOTENT

Remove o recurso especificado do servidor. Chamadas subsequentes costumam retornar 404.

DELETE /api/v1/users/42 HTTP/1.1
HEAD / OPTIONS
SAFE IDEMPOTENT

HEAD: Retorna apenas cabeçalhos (sem corpo).
OPTIONS: Descreve as opções de comunicação para o recurso (CORS preflight).

OPTIONS /api/v1/data HTTP/1.1
Módulo 5

5. Anatomia dos Cabeçalhos HTTP (Headers)

Os cabeçalhos HTTP transmitem meta-informações cruciais para roteamento, gestão de memória, negociação de conteúdo e controle de conexão TCP. São estruturados no formato Nome: Valor\r\n.

Roteamento & Controle de Socket

Host: example.com

Obrigatório no HTTP/1.1! Permite ao Virtual Hosting diferenciar múltiplos domínios servidos pelo mesmo IP/porta no servidor web.

Connection: keep-alive | close

Define se o socket TCP subjacente deve ser mantido aberto para reutilização ou encerrado imediatamente com TCP FIN após a resposta.

Representação do Payload (Entidade)

Content-Type: application/json

Informa ao parser do receptor a codificação MIME dos bytes transmitidos no corpo (ex: text/html, application/json).

Content-Length: 1024

Indica exatamente quantos bytes o receptor deve ler da stream TCP após o CRLF duplo antes de encerrar o parse do payload.

Transfer-Encoding: chunked

Alternativa ao Content-Length para envio de dados em fluxo dinâmico (streaming), transmitindo o tamanho em Hex antes de cada bloco.

Negociação de Conteúdo & Contexto

Accept: application/json, text/plain

O cliente declara quais formatos MIME é capaz de processar na resposta do servidor.

User-Agent: Mozilla/5.0 ...

Identificação da aplicação/cliente que originou a requisição de rede.

Autenticação, Estado & Cache

Authorization: Bearer <token>

Credenciais enviadas para autenticar a requisição (ex: HTTP Basic, JWT Bearer Token).

Cookie / Set-Cookie

Mecanismo para persistência de estado em protocolo *stateless*. O servidor envia Set-Cookie e o cliente devolve Cookie.

Cache-Control: no-cache / ETag: "xyz"

Instruções para proxies e navegadores reduzirem tráfego e requisições desnecessárias através de validação condicional.

Módulo 6

6. Códigos de Retorno / Status HTTP

A primeira linha da resposta do servidor (Status Line) inicia com o código numérico de três dígitos. Os códigos dividem-se em 5 classes principais segundo a RFC 7231:

1xx Informativo
2xx Sucesso
3xx Redirecionamento
4xx Erro do Cliente
5xx Erro do Servidor

Códigos Fundamentais para Engenharia e Diagnóstico

200 OK
Requisição Bem Sucedida O recurso solicitado foi processado e retornado no corpo da resposta.
Padrao GET/POST
201
Created (Criado) Submissão realizada com sucesso resultando na criação de um novo recurso no servidor (usualmente acompanhado do cabeçalho Location).
Comum em POST
204
No Content (Sem Conteúdo) A ação foi executada com sucesso, mas o servidor intencionalmente não retorna payload no corpo (economiza largura de banda).
Comum em DELETE/PUT
301 / 302
Moved Permanently / Found (Redirecionamentos) Instrui o cliente a buscar a URI fornecida no cabeçalho Location. 301 encoraja o cliente/proxy a fazer cache permanente da nova URL.
Redirecionamento
304
Not Modified (Validação de Cache) O recurso não mudou desde a última consulta (verificado via ETag/If-Modified-Since). Zero bytes de corpo enviados pelo socket TCP!
Otimizacao de Rede
400
Bad Request (Requisição Malformada) Sintaxe inválida (ex: ausência do header Host no HTTP/1.1 ou falta de \r\n obrigatório).
Erro de Sintaxe
401 / 403
Unauthorized vs Forbidden 401: Exige autenticação prévia (falta de token ou token inválido). 403: Identidade conhecida, porém sem permissão de acesso ao recurso.
Seguranca
404
Not Found (Não Encontrado) O servidor não localizou qualquer recurso correspondente à URI solicitada na start-line.
Recurso Ausente
500
Internal Server Error Exceção não tratada ou crash no código da aplicação backend (ex: NullPointerException ou Uncaught Error).
Falha na Aplicacao
502 / 504
Bad Gateway vs Gateway Timeout Erros típicos de Proxy Reverso (Nginx/HAProxy): 502 significa recusa de conexão pelo servidor interno; 504 indica estouro de tempo (timeout) de resposta do servidor interno.
Infra / Proxy

8. Roteiro Prático de Laboratório Avançado (100 min)

Siga o roteiro de experimentos abaixo utilizando o terminal (Linux, macOS ou WSL/PowerShell no Windows). Os exercícios cobrem desde a injeção em nível de socket nu até a manipulação de verbos HTTP, codificação de URLs e gestão de cache/redirecionamento.

1

Injeção Manual via Netcat: Socket Nu & Falhas de Sintaxe

Objetivo: Injetar bytes HTTP puros e diagnosticar comportamento perante erros de sintaxe e falta de CRLF.
Passo 1A: Requisição Válida HTTP/1.1 
# Conectar via socket TCP transparente na porta 80
nc -C example.com 80

# Digite as linhas a seguir e pressione ENTER duas vezes ao final:
GET / HTTP/1.1
Host: example.com
User-Agent: TerminalCC/1.0
Connection: close
Passo 1B: Teste do Erro 400 Bad Request (Ausência do Header Host) 
# No HTTP/1.1 o header Host é obrigatório segundo a RFC 7230
nc -C example.com 80
GET / HTTP/1.1
Connection: close
O que você deve analisar:
  • No Passo 1A, verifique o recebimento da linha HTTP/1.1 200 OK e o término do socket ao receber Connection: close.
  • No Passo 1B, observe o retorno do código de status 400 Bad Request devido à violação do Virtual Hosting do HTTP/1.1.
2

Semântica de Métodos HTTP (`GET`, `POST`, `PUT`, `DELETE`, `OPTIONS`)

Objetivo: Executar chamadas com diferentes verbos e inspecionar transmissão de payload e respostas CORS.
A. Envio de Payload com POST (JSON) 
curl -v -X POST https://httpbin.org/post \
  -H "Content-Type: application/json" \
  -d '{"matricula": "20261001", "nome": "Aluno EC"}'
B. Atualização com PUT 
curl -v -X PUT https://httpbin.org/put \
  -H "Content-Type: application/json" \
  -d '{"status": "atualizado"}'
C. Remoção com DELETE 
curl -v -X DELETE https://httpbin.org/delete
D. Inspecionar Métodos com OPTIONS 
curl -i -X OPTIONS https://httpbin.org/get
Ponto de Observação: Verifique como o header Content-Length é gerado automaticamente pelo cURL quando enviamos um corpo (-d), e como a resposta do OPTIONS inclui o cabeçalho Access-Control-Allow-Methods.
3

Anatomia da URL, Query Strings & Percent-Encoding (RFC 3986)

Objetivo: Transmitir parâmetros via URL e analisar a conversão de caracteres especiais para %HEXHEX.
Passo 3A: Envio de Query String Codificada Manualmente 
# Transmitindo espaço (%20), 'ç' (%C3%A7) e '&' (%26) na Query String
curl -v "https://httpbin.org/get?curso=Engenharia%20da%20Computa%C3%A7%C3%A3o&semana=1&tag=%23baremetal"
Passo 3B: Envio de Parâmetros com Encoding Automático do cURL 
curl -G "https://httpbin.org/get" \
  --data-urlencode "busca=sistemas operacionais & redes" \
  --data-urlencode "autor=Tanenbaum & Kurose"
Questão do Lab: Compare o campo "args" retornado pelo JSON do servidor no Passo 3A e 3B. O servidor recebeu os caracteres decodificados corretamente após o parsing?
4

Negociação de Conteúdo & Identificação de Cliente

Objetivo: Alterar o comportamento da resposta modificando cabeçalhos `Accept` e `User-Agent`. 
# 1. Simular uma requisição pedindo explicitamente payload JSON
curl -i -H "Accept: application/json" https://httpbin.org/headers

# 2. Alterar o User-Agent para simular um navegador mobile Android
curl -i -H "User-Agent: Mozilla/5.0 (Linux; Android 14) Chrome/120.0" https://httpbin.org/user-agent
5

Investigação de Redirecionamentos (301/302) e Cache (304 Not Modified)

Objetivo: Rastrear cadeias de redirecionamento e validar economias de banda usando validação condicional via ETag.
Passo 5A: Rastreamento de Redirecionamento HTTP → HTTPS (301 Moved Permanently) 
# Sem a flag -L, o cURL apenas recebe a resposta 301 e o header Location
curl -I http://google.com

# Com a flag -L, o cURL segue automaticamente o redirecionamento
curl -I -L http://google.com
Passo 5B: Testando Validação de Cache Condicional (304 Not Modified) 
# 1. Primeira consulta para obter a ETag do recurso
curl -i https://httpbin.org/etag/meu-vsn-123

# 2. Segunda consulta enviando o header condicional If-None-Match com a ETag recebida
curl -i -H 'If-None-Match: "meu-vsn-123"' https://httpbin.org/etag/meu-vsn-123
Análise do Socket: Observe como na resposta 304 Not Modified o servidor **não envia nenhum byte no corpo**, economizando largura de banda da rede.
